Retry later, and not all at the same moment

Mental model

Two rules: each wait doubles, and each client adds random noise

Exponential backoff doubles the wait after each failure, so a broken server gets fewer and fewer requests. Jitter makes each client wait a slightly different time, so clients that failed together do not retry together.

Where it breaks

Three ways backoff goes wrong

Check

An API returns 400 Bad Request. Should the client retry with backoff?

Retry only errors that can pass: timeouts, 503 and 429. Not 400 or 404.

Check

A gateway, a service and a client each retry 3 times. One call fails at the database. How many calls can the database get?

3 × 3 × 3 = 27. Retry at one layer only, usually the outermost one.

Check

Base 100 ms, no cap, attempt 12. Roughly how long is the wait?

100 ms × 2¹² ≈ 410 s. A cap of a few seconds keeps the client useful.

Put the retry loop in order

Arrange the steps of one attempt.

  1. If the error cannot pass, give up
  2. Call the server
  3. Sleep min(cap, base × 2ⁿ) with jitter
  4. On success, return the result

Call, return on success, give up on errors that cannot pass, otherwise sleep and loop.

Predict

You switch 1,000 clients from no jitter to full jitter. What happens to the peak load?

The total stays the same; the peak falls because the retries are spread over the window.

Recall

Which problem does jitter solve that doubling alone does not?

Doubling slows each client down; jitter breaks the lockstep between clients.

Recall

Which response is worth retrying with backoff?

503 says “try again later”; it is the case backoff was made for.

Recall

Where should retries live in a three-layer call chain?

One retrying layer keeps the worst case at 3 calls instead of 27.

Five lines to keep

  1. Retry only errors that can pass.
  2. Double the wait, up to a cap.
  3. Add jitter, so clients do not move in step.
  4. Retry at one layer only.
  5. Come back when the review box says so.
