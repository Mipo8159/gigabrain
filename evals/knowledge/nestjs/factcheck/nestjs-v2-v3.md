## Nest 12 deltas found

- **Lifecycle "by hierarchy level"** is *within a module*: v12 calls a module's providers level by level (`getInstancesGroupedByHierarchyLevel`, DESC for destroy). v11 used `Promise.all`. The cross-module order is unchanged from v11 (distance-sorted, reversed on shutdown). The brief's line "Lifecycle: ordering is by hierarchy level" should say so.
- **New official reliability packages** (docs section `/reliability/*`, all pre-1.0, published 2026-09-25 to 2026-10-01): `@nestjs/outbox` 0.1.2, `@nestjs/idempotency` 0.0.2 (an app-wide interceptor with `@Idempotent()`), `@nestjs/workflows` 0.0.3 (durable, DB-journaled workflows), `@nestjs/locks` 0.0.3 (`@OnOneInstance()`, `@WithoutOverlapping()`, fencing tokens). None of them are in BRIEF.md.
- **@nestjs/cqrs 12.1:** `commit()` / `publish()` return the publisher's result and accept a dispatcher context (`{ transaction }`); the event publisher is pluggable.
- **Express adapter drains in-flight requests on shutdown** (migration guide, "Other notable release changes").
- **ESM builds change the barrel-cycle failure:** under ESM output a circular import is a TDZ `ReferenceError` at import time, not Nest's "(?)" DI error. The "(?)" error is CJS-only.
- **Unchanged in 12 (verified):** Express 5.2.1 with the `simple` query parser; RMQ `noAck` default true; Kafka on kafkajs with `-server`/`-client` postfixes; the RPC unknown-error payload; the ValidationPipe skip on a missing metatype; transient non-bubbling; `resolve()` semantics; guard order.
- **Docs URLs moved** (techniques/* → application/*, data/*, http/*; recipes/terminus → reliability/terminus). The Angular redirects keep the fragment (`movedTo`), and the old Database page is split by fragment (`DATABASE_SECTIONS`). Every ref anchor in v2 and v3 was checked against the docs' heading slugger (`tools/.../heading.renderer.ts`) on the target page, and all now resolve. `techniques/database#transactions` (v2-q19) was dead; it is now `data/typeorm#typeorm-transactions`, edited by another agent. `techniques/database#async-configuration` (v3-q05) only worked through the split map, so it was rewritten to `data/typeorm#async-configuration`. Other moved paths keep valid anchors (e.g. application/validation#stripping-properties, application/configuration#schema-validation, application/logger#injecting-a-custom-logger, recipes/swc#vitest) and were left alone.
- **Shutdown sequence (v12):** `prepareClose()` → onModuleDestroy → beforeApplicationShutdown → `dispose()` → onApplicationShutdown, with hooks inside each module grouped by hierarchy level. `prepareClose` runs before every destroy hook, so it doesn't change v2-q15's cross-module order (re-confirmed by the probe).
- **Other v12 deltas** (ConsoleLogger structured params on by default, ESM-only packages, Kafka RegExp patterns) touch no question in v2 or v3.

## Cross-file hits (not edited)

- **nestjs-v1-q19 and nestjs-v4-q18** say an esbuild/tsx build fails with "Nest can't resolve dependencies of the X (?)". [probe] (v12.1.3, esbuild 0.25, also v11 `reflectConstructorParams` source): with no `design:paramtypes` at all, Nest sees zero params and **boots**, injecting `undefined`. The "(?)" error appears only if some other parameter carries an explicit `@Inject()`. The keyed answers (tsc/SWC) are still right, but both stems' symptoms are likely wrong. v2-q17 ("undefined dependencies") has it right.
- No other exam file repeats the v2-q04 old message, the v3-q03 `reading 'loadLimits'` claim, the v3-q05 "unconfigured ConfigService" reason, or the "in-memory bus" wording.
